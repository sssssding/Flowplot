# 批量运行的输入稳定性与发布保护

日期：2026-10-13；入口仍为 `check_suite.py`，命令和退出码见 [批量检查](BATCH_CHECK.md)。本轮修复清单解析/指纹不来自同一份字节，以及运行期间来源或已读取报告变化仍可能发布成功结果的问题。

## 现在如何处理

1. 清单通过共同严格读取器一次捕获，解析和 `manifest_sha256` 使用同一份原始字节；上限 64 KiB，拒绝文件链接/目录联接、重复字段、非有限数值和过深 JSON。不能解析旧内容后另读新文件来计算指纹。
2. 开始前捕获正式流程共用的程序/Schema/开发登记指纹。相关文件缺失时不开始新运行；运行结束前再次核对，不只检查规则/Java 两个文件。
3. 评分后、写产物前核对清单和程序/登记；真实读取模式还复核已解析源模型的范围、链接及哈希。
4. 重新读取每个非执行失败案例的报告，比较状态、预测 code 和实际读取的诊断/运行字节指纹。已计分报告变化、partial/unsupported 的证据变化，或原来不可计分的报告后来补齐，都需新建运行，不继续套用旧汇总。
5. 写入 `summary.json` 后重新解析实际字节，核对内存计算结果，布尔值或整数/浮点类型替换不能蒙混；中文 `report.md` 使用 UTF-8/LF。
6. 产物写完后再次检查输入和实际输出字节，再记录最终 `run.json`。正常完成/不完整记录增加 `input_stability_verified: true`、`summary_sha256` 及 `source_fingerprints`；没有因为这些字段而提升独立验收资格。

本次没有修改诊断规则、Java 解析或原模型，没有更改 COMSOL 安全设置。单模型报告格式不变；批量 `check-suite-run-0.1` 增加可选字段，通用评分结果结构及 CLI 退出码保持兼容。

## 失败时看什么

发现变化或写入/复核失败时，顶层 `run.json` 记录 failed，稳定性标记保持 false；中断仍记录 cancelled。发布前失败通常没有汇总，发布中失败可能留下 `summary.json` / `report.md`，工具不覆盖或删除这些排查材料。

**不能只凭汇总文件存在或其中的高 Recall 判断成功。** 必须核对同目录终态；failed/cancelled 不是有效完成结果。修复输入后使用全新目录重跑，不能编辑旧终态或哈希使其看似通过。稳定的单模型执行失败仍保留 failed 且不计分，整组为 incomplete，不因其他模型匹配而成为完整结果。

正式结果读取器同步核对可选汇总哈希/严格布尔稳定性标记，并将可选程序登记指纹与冻结输入比较；即使重新绑定外层哈希，也不能绕过这些一致性检查。缺少新增可选字段的匹配格式记录按原逐报告重算规则读取，不补造“已验证稳定性”字段，也不因此升级版本或资格。

## 这些检查不能证明什么

- 不是操作系统级原子快照/排他锁；其他程序仍可能在最后一次检查后修改文件，或在两次观察间改动并恢复。
- 执行失败案例可能没有报告；工具不伪造诊断来认证原失败原因。持续无效且不可计分的报告不保证其每个无效字节从未变化；它们不作为干净负例计分。
- 文件哈希和稳定性标记不是作者签名、可信运行证明、专业人员身份或真正独立性认证。拥有写权限的人仍可同时伪造全部输入和记录。
- 正式验收仍需真实审核集及冻结/运行/逐报告复核；开发回归、隐藏窗口和故障模拟不能替代专业/独立/新用户验收。

本轮改动涉及 `check_suite.py` 和 `acceptance_result.py`，二者均在正式冻结源码集合中。旧冻结/正式记录需要原匹配版本或按团队流程重新确认，不能手改指纹适配新代码。运行目录及错误文字可能含本机信息，原始日志/模型副本不直接分享。
