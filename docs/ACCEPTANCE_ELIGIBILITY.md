# 批量评分与正式冻结的验收门槛一致性

日期：2026-10-13。修复 `check_suite.evaluate_dataset` 的旧资格门槛与 [正式冻结](ACCEPTANCE_FREEZE.md) 条件不一致的问题；规则算法和模型读取未变。

## 修复了什么

通用批量入口早期只检查独立集/专业审核声明、每例审核信息、五规则覆盖与负对照，并排除原六个开发模型。正式冻结后来增加至少 10 个案例、全部 20 个登记开发模型排除、真实来源/分组与独立性声明、日期规范等条件。之前绕过冻结直接调用通用评分，某些未满足新条件的清单仍可能显示 `acceptance_eligible: true`。

这不是已发生的真实独立成绩作废：团队尚无真实独立集，原六模型与 14 变体始终为开发数据；已有严格冻结入口本身也没有放宽。本轮是在通用评分入口堵住口径不一致。

## 当前行为

1. 批量仍核对基本清单、逐模型报告来源和完整覆盖，并正常计算开发用 TP/FP/FN、Precision/Recall/F1。
2. 旧条件未满足时保留原阻断项，不把开发回归误判为程序故障。
3. 旧条件全部满足后，额外调用真正的 `acceptance_dataset.validate_acceptance` 和完整开发登记；不另写一套宽松条件。门槛模块/登记不可用也拒绝提升资格。
4. 不满足正式条件时，追加 `formal_freeze_requirements_not_met`，`evaluation_kind` 保持 `development_or_unreviewed`，`acceptance_eligible` 为 false，`meets_recall_above_90_percent` 为 null；完整模型上的开发统计仍保留。
5. 不完整覆盖继续单独阻断。通过声明条件也不认证审核人/独立性、物理正确性、严重等级或解释质量。

至少 10 个模型、两个来源组只是准备门槛，不能靠复制改名、轻改开发样本或填造审核字段满足真正独立性。通用评分不创建冻结记录，`acceptance_eligible` 也不是签署证明。正式验收仍按预检 → 冻结 → 运行 → 逐报告复核执行，不用通用汇总替代来源完整的正式记录。

## 对现有记录的影响

旧开发批量统计值及原阻断项保持兼容；本轮对六份既有实测报告再次离线复核，仍 6/6 完整且 code 集合匹配，没有独立验收资格。

正式冻结的源码集合包含 `check_suite.py`，因此本轮源码变动会使旧冻结集版本核验不匹配。需要用原匹配代码复核历史正式记录，或按团队流程重新确认并生成新冻结/运行；不得只改旧指纹或保存分数来升级。

原 `desktop_smoke.json` 保持字节不变，不改历史来源哈希。使用本轮源码真实重跑隐藏桌面集成，将新记录另存为 [desktop_smoke_eligibility_gate.json](../data/fixtures/desktop_smoke_eligibility_gate.json)；当前来源测试使用新记录，旧记录另有完整文件指纹保护。旧可见记录仍保持原来源，不宣称本轮可见界面或新用户验收。

后续 [批量稳定性加固](BATCH_STABILITY.md) 产生新的独立实测记录，当前来源测试以 `desktop_smoke_batch_stability.json` 为准；本页两份先前记录继续按原字节保留，不重新绑定源码。

## 验证范围

- 11 项新增评分专项覆盖：6 个全声明模型、缺独立性声明、全部 14 变体哈希、未来/非标准日期、缺建立人/来源/分组、伪布尔确认、单来源组、大小写重名、鲁棒性标签、登记不可用与正式门槛变更。测试输入和审核声明全部是模拟，不是独立物理模型。
- 另有 1 项旧桌面证据字节保持测试；既有通过资格的模拟测试改为完整 10 例/双组声明，仍不能当成实际审核证据。
- 真实隐藏窗口流程：两次模型副本检查（基准、缺少入口）、批处理启动后的取消、六份报告展示、概览/对比/历史与协作包往返通过。两份极端数值报告仍明确为模拟；原六模型哈希不变，不求解。
- 隐藏测试不是人工可见核验、专业审核、独立模型测试或真实新用户计时；这些待办不因软件门槛修复而完成。

原始记录位于本机 `outputs/acceptance-handoff/20261013/eligibility-gate-desktop-smoke/` 与 `eligibility-gate-offline/`，不上传日志/模型副本。回退本修复时应恢复对应代码/测试及匹配来源记录，并清楚标记旧资格口径；不能只删除新阻断项而继续引用旧汇总为正式验收。
